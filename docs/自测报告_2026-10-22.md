### 2.1 为什么自测要自带桩上游

网关对上游**恒发 `stream=true`**（非流式客户端由 `aggregate_sse_completion` 聚合），所以桩上游一律回 SSE 帧，这样才走的是与生产同一条代码路径。桩支持三种模式：

- `sse_ok`：正常 `content` 流；
- `sse_tool`：`tool_calls` 跨帧分片；
- `json_error`：回任意 `status` + JSON（用来造 `11128` 反探测、`11133` 请求非法等上游错误）。

### 2.2 隔离性

自测**不碰真实运行态**：

- `g.STATE_FILE` → `devtools/_selftest_tmp/state.json`
- `g.wb_usage.configure(path=devtools/_selftest_tmp/usage.json, …)`
- 账号池由 `reset_pool()` 造两个假号（`t1`/`t2`，域名 `www.codebuddy.cn`，积分 500/400），并清空熔断与反探测状态
- 每次启动先 `shutil.rmtree` 重建 `devtools/_selftest_tmp/`

> 踩过的坑（已写进脚本注释）：**不能**用系统临时目录。本机 DSH 文件沙箱对 `%TEMP%\dsh-*\` 下新建文件返回 `PermissionError`，`/v1/switch` 落盘时会直接 `RemoteDisconnected`。

## 4. 本轮发现并修复的问题

### 4.1 未知余额被当成「余额 0」，新号被静默踢出候选池（P1）

**现象**：刚加入的账号在面板上「可用」，但请求永远派不到它；`credit_floor=100` 生效，可号里明明有积分。

**根因**：`wb_pool_policy.scope()` 直接拿 `account.credits` 和下限比，而 `Account.credits` 默认 `0`——「还没采集」和「真的 0 分」在数据模型里长得一模一样。新号在余额采集跑过之前必然被判「积分不足」。

**修法**：

- `Account` 新增 `credits_known: bool = True`（`core/wb_gateway.py:239`，默认 `True` 兼容老 `state.json`）；
- 从凭据文件解析时：`raw_credits = raw.get("credits")`，`credits_known = raw_credits is not None`（`core/wb_gateway.py:1003`）；
- `wb_pool_policy.credits_known(account)`（`core/wb_pool_policy.py:111`），`scope()` 改为 `credit_floor and credits_known(account) and credits < floor`（`:159`）——**余额未知不参与下限过滤**；
- 采集/回填到真值时置 `credits_known = True`（见 4.4）。

**回归**：T19、T20。

### 4.2 聊天派发绕过池策略（P1）

**现象**：`config.json` 里设了 `pool.region=cn`、`pool.credit_floor=100`，但只要「当前账号」还标着可用，请求就一直派给它——区域和下限形同虚设。

**根因**：`_pick_chat_account()`（`core/wb_gateway.py:1973`）只看 `pool._is_available(current)`，没走 `wb_pool_policy.scope()`；策略只在「当前号不可用时」的兜底路径里生效。

**修法**：新增 `_passes_pool_filters(account)`（`:1996`），内部调 `wb_pool_policy.scope([account], region=…, credit_floor=…)`（异常按通过，避免策略模块报错锁死派发）。当前号（`:1973`）与兜底候选列表（`:1983`）都必须过这个过滤。

**回归**：T10、T19、T20。

### 4.3 面板说不出「为什么这个号不派活」（P2）

**现象**：`/status` 里账号显示 `available: true`、`reason: ""`，但请求就是派不到它；出问题时完全看不出是策略挡的还是熔断。

**根因**：`get_status()` 只在 `not _is_available()` 时才算 `reason`；被池策略（区域/积分下限）过滤掉的号既不是「不可用」也没原因。

**修法**：

- `unavailable_reason(account, now=None, credit_floor=0.0)`（`core/wb_pool_policy.py:122`），积分不足时返回「积分不足（0 < 下限 100）」；
- `unavailable_summary()`（`core/wb_gateway.py:532`）把被下限挡住的号也算进不可用摘要；
- `get_status()` 的每账号 `reason` 改为**始终计算**，并新增 `credits_known` 字段。

### 4.4 回填余额后没置「已知」（P2，配合 4.1）

**根因**：`_enrich_pool_credits()` 与 `/status` 的 `live_credits` 回填都只写 `credits/energy`，不置 `credits_known`——于是刚采集到真余额的号，下一轮又因为 `credits_known` 停留在旧值而被误判。

**修法**：`_enrich_pool_credits()` 抽出闭包 `_apply(acc, record)`（`core/wb_gateway.py:1142`）统一写 `credits/energy` 并置 `credits_known = True`；`/status` 的 `live_credits` 回填处（`:1700`）同样补置。

**线上验证**：重启后 `/status` → 冯小秋 `credits=2228 known=True available=True reason=""`；空 `credits=3900 known=True available=True reason=""`；`/panel/api/pool` 的 `unavailable=[]`；`live_credits`: `total_remain=6128 / total_size=8824`。

## 6. 已知限制（本轮**未**覆盖）

| 多模态 / 视觉模型 | `deepseek-v4.1-flash-sg` 等带图请求未做端到端跑图，只验了文本链路 |
| 任务引擎真实跑批 | 本轮只验 `/tasks/list` 与接口结构；真实跑批已在 `03ed44b` 单独实测（新号 14 个任务 0 错误、12 个当场领奖），本轮未重跑以免消耗积分 |

| 上游 `11128` 反探测 | **仍可能发生**。本轮保证的是「不放大、说得清、自动恢复」：成串时回 `429 + Retry-After`、阶梯退避、期间不打上游、任意一次成功即归零 |
| 积分下限语义变化 | 老逻辑「余额 0（含未采集）一律排除」→ 现在「余额未知不参与下限过滤」。若确实想排除零余额号，需等采集跑过一次（`credits_known=True`）后由下限正常生效 |
